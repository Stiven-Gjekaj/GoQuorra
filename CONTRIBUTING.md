# Contributing to GoQuorra

Thanks for your interest.
Contributions of all kinds are welcome: bug reports, documentation fixes, new
features, and arguments against a decision that is already made.

[docs/milestones.md](docs/milestones.md) holds what is not built, and what was
deliberately left.

## Ways to contribute

- Take on something from the milestones, or argue that it is wrong.
- Add a rule to the store contract suite. A rule the interface promises and
  the suite does not check is a rule that will be broken.
- Report a case where a job ends up somewhere it should not, with the steps
  that produced it.
- Improve the documentation. A question you had to ask is a fault in it.

Before you start significant work, open an issue to agree on the approach.
This costs you one message and can save you a rewritten pull request.

## Development setup

You need Go 1.24.
PostgreSQL is optional for most of the work.

    git clone https://github.com/Stiven-Gjekaj/GoQuorra
    cd GoQuorra
    make verify

`make verify` runs everything CI runs.
It needs no database, because 103 of the 128 cases need nothing installed.

To run the 25 that do:

    docker compose -f deployments/docker-compose.yml up -d postgres
    export QUORRA_TEST_DATABASE_URL="postgres://quorra:quorra@localhost:5432/quorra?sslmode=disable"
    make test-postgres

To see the whole thing running:

    make dev

## Where a change lives

| Change | Files |
| ------ | ----- |
| A rule about what happens to a job | `internal/jobs/`, and a table test beside it |
| A rule about storage | `internal/store/storetest/`, then both stores |
| A new HTTP route | `internal/api/` |
| The worker protocol | `proto/quorra/v1/quorra.proto`, then `make proto` |
| What a worker does | `worker/` |
| The dashboard | `internal/api/dashboard.html` |
| The schema | `migrations/`, and the contract suite applies it |
| Something not built yet | `docs/milestones.md` |

## The rules that catch people

[`AGENTS.md`](AGENTS.md) is the full set, and it applies to a person as well
as to an agent. These five cause the most rework.

- **One change per commit, and a feature is many commits.** A commit that says
  "integrate the full feature" is wrong even when the code is right.
- **Code and its tests go in one commit. Documentation goes in its own.**
- **All text uses Simplified Technical English.** Short sentences, active
  voice, present tense. No em-dashes and no emoji, in source, comments,
  documentation, commit messages, or pull requests.
- **A new rule about a job goes in `internal/jobs`.** Not in a SQL statement
  and not in an HTTP handler. That package holds no database handle and reads
  no clock, and that is the only reason its tests run with nothing installed.
- **A new rule about storage goes in the contract suite first.** Then both
  stores are made to pass it. A rule added to one store alone is a rule the
  other one quietly breaks.

## Four traps that this design creates

**A test can pass for the wrong reason.**
Put the fault back and watch the test fail before you trust it.
The retry limit test was checked by restoring the old comparison, and three of
its four cases failed.
A test that has never failed is a test nobody has checked.

**A test can skip instead of running.**
The suite this project replaced skipped every case when PostgreSQL was
missing, and reported success for a module that did not compile.
If you add a test that needs something installed, make it fail loudly when
that thing is required and absent.

**Assert a property, not a byte.**
JSONB does not return the bytes it was given: it reorders the keys and drops
the spaces.
Compare a payload by what it means.
A byte comparison passes against the in-memory store and fails against
PostgreSQL, for a reason that has nothing to do with either being wrong.

**Do not read the clock in a function that decides something.**
Take the time as a parameter.
Every store here takes a `func() time.Time`, which is what lets a test move
time forward and watch a lease expire in microseconds rather than in the
thirty seconds it takes in production.

## Do not edit the generated code

`internal/quorrapb` is generated from `proto/`.
Change the protocol, then run:

    make proto

Commit the result.
`make proto-check` regenerates it and fails on a difference, and CI runs that.

The check exists because this repository once carried two files headed "Code
generated by protoc-gen-go. DO NOT EDIT." that were written by hand.
Their messages were plain structs rather than protobuf messages, so gRPC
refused every call at run time.
The code compiled and read correctly in review.

## Dependencies

There are five.
Say in the pull request why the standard library does not do the job.

Two were removed during the rebuild, and both are worth knowing about before
you add one back.
`chi` went because Go 1.22 gave `net/http` the method and wildcard patterns it
was there for.
`cobra` went because the command line tool is four verbs, and the standard
library covers that in less code than the dependency.

## Before you open a pull request

    make verify

That is the same set CI runs.
If you touched storage, also run `make test-postgres`.

Add tests for anything you change, and put them in the same commit as the
code.

## Commit messages and pull requests

- Write the subject in the present tense. It says what the change does.
- Put no version number in a subject line, and change no version in a commit.
- Say in the body what changed, why, and what you measured.
- Do not add a footer saying that a tool wrote the text, and do not add a
  `Co-Authored-By` line. A commit shows that a human read the code.

## Reporting security issues

Do not open a public issue for a security problem.
See [SECURITY.md](SECURITY.md) for how to report it privately.
